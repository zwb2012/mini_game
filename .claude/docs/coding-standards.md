# 编码规范

- 所有游戏代码必须在公共 API 上包含文档注释
- 每个系统必须在 `docs/architecture/` 中有对应的架构决策记录 (ADR)
- 玩法数值必须数据驱动（外部配置），禁止硬编码
- 所有公共方法必须可单元测试（依赖注入优于单例）
- Commit 必须引用相关的设计文档或任务 ID
- **验证驱动开发**: 添加玩法系统时先写测试。UI 变更用截图验证。将预期输出与实际输出对比后再标记工作完成。每个实现都应有验证其正确性的方式。

# 设计文档规范

- 所有设计文档使用 Markdown
- 每个机制在 `design/gdd/` 中有独立文档
- 文档必须包含以下 8 个必要章节:
  1. **概述** —— 一段话总结
  2. **玩家幻想** —— 预期的感受和体验
  3. **详细规则** —— 无歧义的机制描述
  4. **公式** —— 所有数学公式含变量定义
  5. **边界情况** —— 已处理的异常情况
  6. **依赖** —— 列出关联的其他系统
  7. **调优参数** —— 标识出的可配置值
  8. **验收标准** —— 可测试的成功条件
- 平衡数值必须链接到其来源公式或设计理由

# 测试规范

## 按 Story 类型的测试证据

所有 Story 在标记为 Done 之前必须有相应的测试证据:

| Story 类型 | 必需证据 | 位置 | 门禁级别 |
|---|---|---|---|
| **逻辑**（公式、AI、状态机） | 自动化单元测试——必须通过 | `tests/unit/[system]/` | 阻塞 |
| **集成**（多系统） | 集成测试或文档化的可玩性测试 | `tests/integration/[system]/` | 阻塞 |
| **视觉/手感**（动画、VFX、手感） | 截图 + 主管签字 | `production/qa/evidence/` | 建议 |
| **UI**（菜单、HUD、界面） | 手动走查文档或交互测试 | `production/qa/evidence/` | 建议 |
| **配置/数据**（数值调优） | Smoke check 通过 | `production/qa/smoke-[date].md` | 建议 |

## 自动化测试规则

- **命名**: 文件用 `[system]_[feature]_test.[ext]`；函数用 `test_[scenario]_[expected]`
- **确定性**: 每次运行必须产生相同结果——不用随机种子，不依赖时间的断言
- **隔离**: 每个测试自行设置和清理状态；测试不能依赖执行顺序
- **数据驱动**: 使用常量文件或工厂函数提供测试数据，不写内联魔法数字（边界值测试除外——此时精确数字就是要点）
- **独立性**: 单元测试不调用外部 API、数据库或文件 I/O——使用依赖注入

## 什么不自动化

- 视觉保真度（shader 输出、VFX 外观、动画曲线）
- "手感"质量（输入响应性、感知重量、时机）
- 平台特定渲染（在目标硬件上测试，不 headless）
- 完整玩法 session（由可玩性测试覆盖，不自动化）

## CI/CD 规则

- 每次 push 到 main 和每个 PR 时运行自动化测试套件
- 测试失败禁止合并——测试是 CI 中的阻塞门禁
- 绝不通过禁用或跳过失败测试来让 CI 通过——修复根因
- 引擎特定 CI 命令:
  - **Godot**: `godot --headless --script tests/gdunit4_runner.gd`
  - **Unity**: `game-ci/unity-test-runner@v4` (GitHub Actions)
  - **Unreal**: headless runner with `-nullrhi` flag
